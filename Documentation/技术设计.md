# SceneScope 技术设计

[项目说明](../PROJECT.zh-CN.md) · [English](Architecture.en.md)

## 目标与边界

这个工具展示 Unity 编辑器工程与性能排查能力：静态模块在主线程安全访问场景，将规则诊断组织成可解释数据，在 Scene 视图中定位问题，以 Undo 完成有限的场景修改；1.1 新增 Runtime 模块，在 Editor Play Mode 或 Development Build 中记录运行时观测，并将两类结果分别输出为可复查的报告。

静态模块检查已加载的普通场景及其中 Renderer 引用的材质、纹理；静态扫描本身不测量 Draw Call、GPU 耗时或 FPS。Runtime 模块单独采集帧间隔、CPU/GPU 时间、GC 分配与回收计数、内存和实际渲染计数，但不包含函数调用栈、GC 暂停归因或逐 Draw Call 分解，也不自动断定 CPU/GPU 瓶颈。预算是可调整的项目约束，而非 Unity 官方硬性限制。

两个入口分别为 **Tools → SceneScope → 打开诊断面板** 和 **Tools → SceneScope → 运行时性能排查**。接入与实测流程见 [运行时排查指南](运行时排查指南.md)。

## 包与职责

工具使用 embedded UPM package：`Packages/com.scenescope.diagnostics`。Editor asmdef 包含场景扫描、静态面板和运行时排查面板，只在编辑器平台编译。1.1 新增独立的 `SceneScope.Runtime` asmdef 与 `SceneScopeCapture` 组件，可进入 Player，且不引用 UnityEditor；实际采集代码通过 `UNITY_EDITOR || DEVELOPMENT_BUILD` 限制，正常 Release 构建中的启动入口不采样。工具不会自动向所有场景添加组件，不依赖远程服务或第三方包。

| 层 | 职责 |
| --- | --- |

## 运行时采集与证据边界

采集器显式启动后建立 ProfilerRecorder，并核对计数器名称和单位；未公开、不可用或尚未收到有效观测的指标保留为 `-1`。逐帧数据写入预分配的结构体环形缓冲区，默认保留 3600 个样本，上限 120000；满后覆盖旧样本。快照、排序统计、分析和导出在手动触发或停止时执行，会产生额外工作。预分配不代表整个工具已经实测零分配或零开销，Unity API、Profiler 和编辑器窗口仍需测量。停止、禁用、销毁及异常路径负责释放 Recorder。

帧间隔来自 `Time.unscaledDeltaTime`，CPU 与渲染计数来自运行时 ProfilerRecorder；GPU 通过 FrameTimingManager 异步获取，并使用 `frameStartTimestamp` 去重。Main Thread 包含同步和限帧等待，不代表纯 CPU 计算；GPU 观测不强行对应同一 CPU 帧；GC 分配和 `GC.CollectionCount(0)` 增量不是 GC 暂停时间。Editor 窗口与工具自身开销也可能污染观测。报告保留设备、图形 API、VSync、目标帧率、计数器来源及可用性，帮助复查这些条件。

所有统计仅覆盖环形缓冲区当前保留的样本，报告用 `droppedSamples` 表示已覆盖的旧数据。分析只给出“超出预算”“发现分配”“部分计数器不可用”等可解释线索，并引导使用 Profiler、Frame Debugger 或平台 GPU 工具继续定位，不根据单个指标自动认定因果关系。

Runtime JSON 使用独立的 2.x Schema，导入前限制文件为 128 MiB、样本为 120000，校验必要结构、数值有效性和样本顺序。CSV 保留原始 `-1` 与 GPU 时间戳；HTML 对动态文本进行编码，不访问外部资源，使用最多 1200 个峰值区间展示趋势，含缺失数据的区间留空。静态诊断与运行时报告使用不同模型，不能互相导入或将静态评分当作性能结果。

## 增量扫描

Unity 对象访问保留在编辑器主线程。交互扫描注册到 `EditorApplication.update`，每次更新以 **6 ms 为软时间预算** 执行多个小步骤。步骤按发现 Transform、检查单个 GameObject、检查单张纹理推进，再执行汇总规则。同步入口为批处理和自动验证提供同一套规则。

6 ms 不是严格延时上限：单次规则、Unity API 调用、根对象发现或最终排序可能独自超过预算，大型场景仍需测量响应时间。这里选择可取消的主线程增量遍历，避免错误地将 Unity API 放到后台线程。取消、脚本重载和进入 Play Mode 会解除更新回调；异常会终止扫描并通知面板。

扫描开始复制设置并记录 UTC 时间与场景路径。结果是一次检查快照，扫描期间场景编辑可能使它过时；关键比较应在场景状态稳定时重扫。未激活对象按设置选择是否纳入，Preview Scene 不在默认场景范围。

## 规则与统计

`ISceneRule.Analyze(ScanContext context, GameObject gameObject)` 是扩展接口，通过 `SceneScanner.RegisterRule` 注册、`UnregisterRule` 移除。自定义规则通过 `context.Add` 追加包含规则编号、描述、建议、定位信息的数据，不应在扫描阶段修改场景。

渲染规则读取 `sharedMaterials`、`sharedMesh`，避免实例化材质。三角形通过 submesh 拓扑与 index count 统计，无须为了读取顶点而开启 Read/Write。材质和纹理使用 HashSet 去重；几何量按 Renderer 实例累计，全部 LOD 都会被纳入，不冒充实际渲染量。

纹理内存调用 `Profiler.GetRuntimeMemorySizeLong`，用于提供数量级线索；它受编辑器、平台和导入状态影响，不能作为设备显存测量。该 API 返回 Unity 对象的 native-memory，Profiler 不可用时返回 0，零值不能据此证明无内存开销。参见 [Unity 2022.3 内存 API 文档](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Profiling.Profiler.GetRuntimeMemorySizeLong.html)。物理检查使用 `MeshCollider.attachedRigidbody`，覆盖父级 Rigidbody 情况。层级检查只在分支首次超过预算的位置报告，降低重复噪声。

评分为 `max(0, 100 - 12×错误数 - 3×警告数 - 提示数)`。它是对规则结果的简单压缩，不是模型预测。比较前后结果需保持规则、阈值和扫描范围一致；不同规模或不同内容场景的分数不具备直接性能可比性。

## 安全修改与 Undo

当前唯一自动修改是关闭小物体 Renderer 的阴影投射。操作前展示具体对象与属性变化，并说明画面可能变化。应用时重新解析目标，去重，过滤资产对象、无效或未加载场景、Preview Scene、投影已关闭和 Shadows Only 对象。

修改使用 `Undo.RecordObject`，将本次操作合并为一个撤销组；同时记录 Prefab 实例属性变化，标记对应场景 dirty，但不替用户保存。Unity 文档要求修改 Prefab 实例后记录其属性变化，见 [Unity 2022.3 Undo.RecordObject](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Undo.RecordObject.html)。纹理导入器、MeshCollider、脚本引用等涉及资产重导入或行为变化的检查只给出建议。

这个设计把“找到问题”“决定视觉取舍”“写入修改”分开，使工具在作品集演示中能展示可审查与可回滚的编辑器操作，而不依赖所谓一键万能优化。

Scene 视图可视化使用 `SceneView.duringSceneGui` 的编辑器绘制回调，将诊断对象的边界和严重程度联系起来；此事件用于 Scene GUI 与自定义 Handles，见 [Unity 2022.3 SceneView.duringSceneGui](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SceneView-duringSceneGui.html)。

## 报告设计

JSON 用 `JsonUtility` 序列化模型字段，不保存内存中的 Unity 对象引用；GlobalObjectId 和路径作为定位证据保留。枚举按 Unity 的整数形式输出，评分由问题严重程度重新计算。

HTML 是静态 UTF-8 文件，包含指标、严重程度分布、按分类分组的全部问题证据、建议、对象路径、资源路径、扫描时间及本次阈值。动态文本统一 HTML 编码，避免场景名称或建议文本被解释成标签；页面不加载外部字体、图像或脚本，并通过 CSP 禁用网络资源与脚本。响应式和打印样式允许浏览器阅读与 PDF 留档。

## 演示与验证设计

演示在工程 Assets 下生成独立目录，已有目录使用新后缀，以便重复演示。四个展区让对象级问题能在场景中被定位，同时为规则验证提供确定样本。批处理入口为 `SceneScope.Editor.SceneScopeValidation.RunBatch`。

`SceneScope.Editor.SceneScopeCI.ScanBuildScenes` 将相同扫描器接入 Unity batchmode，先验证全部启用 Build Scene 的路径，再逐个单独加载并输出带序号的 JSON/HTML，避免将互斥关卡的监听器与预算错误合并。`summary.json` 汇总错误、警告和报告路径；`-sceneScopeFailOnError` 将错误级问题转成退出码 2。实际 Additive 组合仍需额外组合检查。它与验证入口不同：CI 面向工程 Build Settings，验证入口面向确定性测试样本。`Open-SceneScope.ps1` 则是本地交互启动脚本，按工程版本寻找编辑器并调用 `SceneScopeShowcase.Open`。

验证关注行为边界：是否发现已构造的问题、是否正确排除未激活对象、提高预算是否消除对应告警、阴影修复是否修改目标且可撤销、报告是否包含结构化数据及经过转义的文本。它不替代真实设备上的 CPU/GPU 性能采样、复杂项目兼容性验证或大规模压力测试。

这里描述的是实现与验证设计。只有实际运行产生的 `artifacts/validation.json` 及 Unity 日志才能证明本次验证结果；未运行或未覆盖的环境不能记为已通过。
