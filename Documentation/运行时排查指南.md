# SceneScope 运行时性能排查

[English guide](Runtime-Guide.en.md)

SceneScope 的场景诊断器检查静态资源与配置；新增运行时窗口记录游戏运行时的帧间隔、CPU 主线程和渲染线程时间、GPU 时间、托管分配、回收次数、内存及实际 Draw Call / Batches / SetPass / 三角形 / 顶点计数。先捕获可复现的卡顿样本，再用 Unity Profiler、Frame Debugger 或平台工具深入验证原因。

当前面向 Unity 2022.3。不同平台、图形 API、渲染配置和构建方式公开的计数器可能不同；工具不会把缺失指标当成零。

## 在 Editor 中复现

1. 打开要排查的游戏场景，进入 **Tools → SceneScope → 运行时性能排查**。
2. 根据项目设置目标 FPS、卡顿倍率、保留帧数及 GC / Draw Call / SetPass 警戒值。默认目标 60 FPS，卡顿阈值为帧预算的 1.5 倍，即严格超过 25 ms。阈值是项目配置，不是跨项目通用的合格标准。
3. 手动进入 Unity Play Mode，点击 **开始采集**。默认先丢弃 30 个预热样本。
4. 复现实际操作：进入战斗、同时生成敌人、打开大界面、加载资源或切换场景。保持画质、分辨率、相机和操作路径一致。
5. 点击时间轴或卡顿观察点，查看选中观测的 CPU、GPU、GC 和渲染计数。窗口会保留最近的有限数量样本，可以关闭“跟随最新”并拖动历史滑块。
6. 点击 **停止并分析**，查看平均 FPS、P50/P95/P99、卡顿样本数及排查建议。也可以在记录过程中手动分析快照；快照、分析和导出会分配内存并执行额外工作，其附近的数据可能受工具自身影响。
7. 导出 **JSON** 供后续重新打开，导出 **CSV** 分析原始观测，或导出 **HTML** 分享离线图表与诊断线索。

Editor 里的 Scene 视图、Inspector、其他编辑器窗口和 SceneScope 自身绘制都会产生额外开销。Editor 采集适合复现和初步定位；最终性能结论应来自相同目标设备上的可重复测试。

## 在真实游戏项目和开发包中采集

把 `Packages/com.scenescope.diagnostics` 作为本地 UPM 包接入项目。运行时程序集 `SceneScope.Runtime` 不引用 UnityEditor，采集器只在 `UNITY_EDITOR` 或 `DEVELOPMENT_BUILD` 中工作。正常 Release 构建中采集入口不启动采样；工具不会自动在所有场景添加对象，也不会默认打开游戏中的采集。

在测试用启动场景的 GameObject 上添加 **SceneScope → Runtime Performance Capture**（组件类型 `SceneScope.Runtime.SceneScopeCapture`）：

- `Auto Start`：组件开始运行时自动采集。只添加到你需要测试的场景或调试入口。
- `Configuration`：目标 FPS、预热帧数、保留样本数和各项阈值。
- `Export On Disable`：禁用或销毁**仍在采集**的组件时，停止并导出 JSON / CSV / HTML。
- `Export Directory`：留空时输出到 `Application.persistentDataPath/SceneScope`，也可配置目标平台允许写入的目录。

使用 **Development Build** 在目标设备运行。需要 GPU 数据时，检查项目 **Player Settings → Other Settings → Rendering → Frame Timing Stats**，并确认目标平台和图形 API 支持计时。未启用、未收到有效计时或当前环境不支持时，GPU 显示 N/A；工具不会擅自更改项目的图形设置。

复现完成后通过已有调试入口禁用采集组件，或使用项目代码显式停止并导出。不要依赖移动系统强杀进程触发 `OnDisable`，应在可控的测试结束点保存结果。普通场景组件会随所在场景销毁；跨场景测试需要项目自行决定组件生命周期。

显式停止并导出的示例：

```csharp
using System.IO;
using SceneScope.Runtime;
using UnityEngine;

public static class SavePerformanceCapture
{
    public static void Finish(SceneScopeCapture capture)
    {
        var report = capture.StopCapture();
        if (report == null) return;

        var directory = Path.Combine(Application.persistentDataPath, "SceneScope");
        RuntimeReportExporter.ExportJson(report, Path.Combine(directory, "last-capture.json"));
        RuntimeReportExporter.ExportCsv(report, Path.Combine(directory, "last-capture.csv"));
        RuntimeReportExporter.ExportHtml(report, Path.Combine(directory, "last-capture.html"));
    }
}
```

此示例使用固定文件名，会替换该目录下同名报告；需要保留多轮测试时请加运行编号或时间戳。显式调用 `StopCapture()` 后，`Export On Disable` 不会再自动导出同一轮，须像示例这样自行导出。导出在调用线程同步执行，建议安排在测试结束时。

按项目已有且经过授权的文件获取方式，把设备上的 JSON 复制到开发机。在运行时排查窗口点击 **导入真机 JSON**，即可查看采样、统计、设备信息和指标支持情况；不需要该设备保持在线。该流程不包含设备安装、远程连接、自动抓取或设备安全设置修改。

## 怎么读这些指标

| 观测 | 可以得到的线索 | 继续验证的方式 |
| --- | --- | --- |
| 帧间隔、P95/P99、最长帧 | 卡顿出现在哪一段，尾部延迟是否改善 | 同一复现操作重复采样，检查 Profiler 对应时间段 |
| CPU Main Thread / Render Thread | 线程墙钟耗时是否较长 | Profiler CPU Usage 的 Timeline / Hierarchy，区分脚本、物理、加载、驱动和等待 |
| 等待 marker | 可能存在限帧、VSync、呈现或线程同步等待 | 结合 VSync、targetFrameRate 和具体 marker 核实；不能直接当成 GPU 瓶颈 |
| GPU 时间 | 收到的 GPU 样本是否超出帧预算 | 目标设备 GPU Profiler 或平台图形工具，检查阴影、透明叠加、后处理和 Shader |
| GC Allocated In Frame | 哪些观测出现较大托管分配 | Profiler 的 GC.Alloc 调用栈，定位字符串、临时集合、装箱、频繁实例化等 |
| GC 回收次数 | 采样期间第 0 代回收计数是否增加 | CPU Timeline 的 GC.Collect / 增量 GC 标记，确认耗时和卡顿是否重合 |
| Draw Calls / Batches / SetPass | 实际引擎绘制与状态切换计数是否超出项目阈值 | Frame Debugger 检查绘制顺序、Shader Pass、材质和不能合批的原因 |
| GC Used Memory / Total Used Memory | 当前运行时提供的内存占用趋势 | Memory Profiler 检查分配来源和生命周期；这不是独立的 GPU 显存统计 |

CPU Main Thread 包含等待，不能等同于纯 CPU 计算时间或 CPU 使用率。Main Thread、Render Thread 和等待时间可能重叠，不能直接相加，也不能简单相减推算准确工作量。

GPU 计时异步返回，采集器通过 `gpuTimestamp` 去重，只保存新且有效的计时。某一行的 GPU 值表示“采集时收到的 GPU 观测”，不保证对应同一行的 CPU 帧；不能凭同一行高值就认定因果关系。

GC 分配是字节数，GC 回收计数是次数，两者都不是 GC 暂停毫秒。工具没有自动归因到某个函数、对象或 Draw Call，也不会根据一个峰值自动修改游戏代码或渲染设置。窗口提供 Unity Profiler 和 Frame Debugger 的快捷入口，深入定位仍在这些工具中完成。

## 报告范围和格式

- 采样使用预分配环形缓冲区。默认保留 3600 个样本；上限 120000。满后覆盖最早数据，报告记录 `droppedSamples`。**所有统计只对应当前保留窗口，不代表整段会话。** 开始时间与快照时间不能被当成完整数据覆盖时长。
- JSON 包含 `schemaVersion`、设备/Unity/图形 API、采集设置、指标来源及可用性和逐样本原始数据。当前主版本为 2；导入拒绝其他主版本、缺少必要结构、超过 128 MiB、超过 120000 样本以及非有限/非法负值数据。样本的帧号必须严格递增，经过时间不能倒退。
- CSV 使用固定英文表头、InvariantCulture 小数点和 CRLF 换行。包括 `gpuTimestamp`，所有原始未知值保留为 `-1`，便于脚本区分“零开销”和“没有数据”。CSV 不包含完整设备和阈值元数据，应连同 JSON 留存。
- HTML 可直接离线打开，无外部脚本或资源。包含帧时间分位数、FPS、GC 与 Draw Call 汇总、排查建议、最慢 20 个卡顿样本、指标来源和限制。
- HTML 曲线最多绘制 1200 个区间，各指标保留区间峰值。含缺失数据的区间留空，不跨缺失值连线；可能省略区间内部分有效观测。不同指标的区间峰值可能来自不同帧，完整数据以 JSON / CSV 为准。
- HTML 和编辑器中的 `N/A` 表示未知/不可用，原始数据为 `-1`；指标能力为“可用”也不保证每一帧都有数据。
- 观测帧号是采集运行实例中的 `Time.frameCount`，不等于 Profiler 窗口的帧索引。跨进程、跨次运行时，应结合复现步骤和时间段定位。

## 做一次能解释结果的优化验证

选定同一设备、图形 API、分辨率、画质、帧率上限和操作路线，先预热并采集基线。根据线索进入 Profiler 或 Frame Debugger 找到具体热点，只改动已确认的原因，然后重复同一测试并分别保存报告。比较帧时间分布、P95/P99、最慢帧、分配和渲染计数，同时检查画面和功能是否退化。Development Build 和采集本身都有开销，最终发布体验还应在正式构建中验证。

本工具提供可复查的性能证据和排查入口。某个指标下降不自动等于游戏更流畅，某个指标未超阈值也不能证明项目不存在性能问题。

## 本次验证记录

2026-10-23，在本机 **Unity 2022.3.62f3 / Windows / Direct3D11** 上完成检查。分析、报告导入导出、运行时窗口构造及 Development / Release Player 构建共 **16/16 项通过**；Development Player 的采集与生命周期检查共 **13/13 项通过**；Release Player 实际运行检查 **1/1 项通过**，确认启动采集入口后没有启动 Recorder 或历史采样。运行时相关检查合计 **30/30 项通过（16 + 13 + 1）**。

测试夹具主动注入 CPU 工作、托管分配和回收，并向 RenderTexture 离屏绘制以验证实际渲染计数。记录到 267 个样本、CPU 主线程峰值 55.9282 ms、2 个卡顿样本、最长帧约 55.946 ms、单次观测 GC 分配 4,194,336 字节、2 次回收以及非零 Draw Call 计数 65。这些数字用于证明采集器能观察到已构造的负载，**不是实际游戏或移动设备的性能验收结果**。

本次 **GPU 有效样本为 0**，按设计保留为未知值并显示 N/A；该项只覆盖缺失数据处理，不代表 GPU 时间测量已成功。目标设备的 GPU 计时仍需在受支持配置下单独实测。
